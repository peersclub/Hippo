Quick start

Assetworks Exchange is a self-contained venue with its own HMAC-signed trade API, fill engine, wallets and positions, streaming live prices from public exchange feeds. Hippo embeds as a parasite via one <script> tag and trades through the execution seam, so an order the conversational panel places lands in the same book and same wallet (trader-1) as the host's own order ticket.

Test against the deployed stack — nothing to install.

How to read this

Each matrix row is one testable case. What to say / click is literally what you type into the panel composer or which control you press — phrasings marked EVAL are drawn from the labeled intent-accuracy set (evals/queries/v1-intents.jsonl), so they are known-good, not invented. Expected is what the product should do. Surface says where to watch.

SurfaceMeans
PanelThe Hippo panel itself — the card thread inside the parasite
Host pageThe exchange page around it — chart, order ticket, blotter, header
Admin / Portal / Host settingsThe three operator consoles
One rule underneath everything: numbers are retrieval, prose is generation. Every price, stat and sparkline comes from the market-data feed or the venue; the model only writes sentences, so it cannot invent a number. And nothing executes without an explicit confirm — Hippo prepares, you approve.

Matrix — asking instead of guessing NEWEST · AUG 4

A low-confidence read of a costly intent stops and asks. Costly means it spends something you cannot take back cheaply: money (action), durable server state (alert), or the page under your hands (host_action). Cheap intents — research, concept, portfolio, orders, smalltalk — never clarify, because being wrong there costs a re-ask.

What to say / clickExpectedSurface

Whether any given sentence lands under the threshold is the classifier's call, so treat these as likely rather than guaranteed — close btc is the one verified against the deployed gateway.Panel
Tap the safe escape optionThe chosen reading runs through the normal execution path with confidence pinned high, so it can never re-ask. Nothing is placed, armed or posted to the host page. The card settles permanently and swaps its options for YOU CHOSE + the label you picked.Panel
Tap the risky option deliberatelyThe original classification replays untouched — the same order payload, the same ticket, the same confirm. No order logic is duplicated behind the question.Panel

Ask why is BTC moving today? badly wordedNo clarification. Research is cheap.Panel
The confidence policy, in full: threshold 0.85. The classifier's numbers are bimodal by construction — deterministic fast paths return 0.92–0.97 ("we parsed this"), rule fallbacks return 0.6–0.8 ("we guessed this") — so 0.85 sits in an empty gap, and a Python test asserts the gap stays empty so a future 0.87 branch fails loudly. Each card carries 2–4 options (one is not a question; five is a menu) and always at least one non-mutating escape — if the gateway cannot build one it emits no card at all rather than a single-answer "question". TTL 2 minutes, at most 4 open per session, live-object only. Every string on the card is server-authored and rendered verbatim; the panel never invents or re-words an interpretation. Degraded mode deliberately skips clarification — the fallback classifier pins confidence at 0.5, and its deterministic parse of "buy 0.05 btc" is a parse, not a guess.

Walkthrough — the interactive order card

  1. Say long 0.5 BTC 10x. an editable draft card, not an instant ticket: leverage slider, size input, market/limit dropdown, margin dropdown, symbol dropdown, stop-loss and take-profit inputs, and a live price row ticking in real time for that symbol
  2. Drag the leverage slider. it is bounded by the venue's max leverage read from /v1/capabilities — you cannot slide past what the venue allows
  3. Switch Order type to Limit. the price input becomes editable, prefilled from the live price; on Market it is read-only and reads "≈ market"
  4. Edit the size and tap the card's confirm button. the prepared ticket appears carrying your edited leverage / price / margin → confirm → PLACED · WORKING → FILLED
  5. Try to cheat: submit is disabled at size 0, and a tampered client sending leverage above the venue max is rejected server-side ("outside this venue's 1–50× range"). The card only echoes edits — validation lives on the server.
  6. Tap Dismiss instead. the card settles to "Order draft dismissed"; nothing is prepared. The dismissal is also recorded as an implicit misunderstanding signal.
  7. Go offline and reopen a draft. the confirm button is disabled with the title "Reconnect to confirm orders". Trading actions are never queued — they fail loud.
  8. Price sync: open the demo on ?pair=ETH/USDT or switch the host's pair. the draft card and research default to that symbol, and the panel's price matches the host header — the host forwards its exact ticker over a validated postMessage bridge, with server price ticks (~4s) as the always-on fallback
Three price-sync modes via data-hippo-price-source: server (default — the gateway streams transient price ticks for the page's symbol; they never enter the resume journal), client (the SDK subscribes to the same public ticker feed the host uses), host (bridge only). The host bridge is always listened to regardless, and an explicit host price wins, so panel price ≡ page price. There is no user-facing control for this — it is an embed attribute, settable from the host settings page.

Walkthrough — the two confirm surfaces

Who shows the trader the final "yes" is a per-venue decision. Flip it on the exchange page's gear → venue admin drawer (or in host settings under Venue behaviour): it writes the host's /admin/config and the parasite reads it live at confirm time — no restart.

SurfaceBehaviour
api (default)Hippo confirms in its own panel and places directly with the scoped key. The order then appears in the host blotter.
js_callbackHippo hands off and the host renders its own confirm modal ("Assetworks Exchange · confirm order", with Decline and Confirm & place). Nothing places until you approve there.
  1. Switch the confirm surface to Host modal (js_callback), then place an order from Hippo. the host's own modal appears; the panel's card waits
  2. Press Confirm & place. the panel card moves to PLACED ON THE VENUE — WORKING and then reconciles the real order like any other
  3. Repeat and press Decline. the card settles cancelled with DECLINED ON THE VENUE
  4. Repeat and simply walk away for 90 seconds. CONFIRMATION TIMED OUT — CHECK THE VENUE. The handoff expires host-side; the panel never claims an outcome it does not have.
Still open: only these two surfaces are wired. Deep-link and partner-hosted-modal variants need a real pilot partner and are not claimed as working.

Walkthrough — protective exits (stop-loss / take-profit)

Stops and targets ride the same draft → prepare → confirm path as everything else, then become real OCO children on the venue: the take-profit is a reduce-only maker limit, the stop is an adverse-trigger market close, and filling one cancels its sibling.

  1. Say buy 1 ETH with stop loss 3000. EVAL the draft card opens with the Stop loss field prefilled at 3,000
  2. Say long 0.5 BTC 10x stop 60k tp 75k. EVAL both fields prefilled — 60,000 and 75,000. The shorthand sl/tp, the long forms stop loss/take profit, and k suffixes all parse
  3. Say buy 0.5 btc at 60000 with a stop loss at 55k and a take profit at 70k. EVAL a limit entry at 60,000 and both exits — the connectors ("with", "and", "a") are stripped without breaking the limit-price parse. This exact sentence used to parse no order at all; it is now a regression test.
  4. Say sell 0.4 btc at 71000 with a stop at 73k. EVAL a sell limit at 71,000 with a protective stop above it — direction-sane for a short exposure
  5. Confirm one with both exits set. the seam validates the ordering against the actual entry before anything reaches the venue, then places the OCO children alongside the parent
  6. Point the seam at a venue that does not support protective exits. the whole order is declined rather than silently placed without its protection — dropping the stop and filling the entry is the one outcome that is worse than not trading

Walkthrough — the clarification loop end to end

  1. Type close btc. a clarification card. Check the host blotter: no order exists. This is the case verified on the deployed gateway.
  2. Read the options. the first is exactly what the turn would have done, with a hint naming the consequence ("You review and confirm on Assetworks — nothing executes from here."). The rest are genuine non-mutating readings of the same sentence, each hinting "nothing is placed".
  3. Pick Show me my orders first. the consolidated orders card renders; the clarification card settles to YOU CHOSE + that label; still no order
  4. Type close btc again and this time pick the first option. the normal close flow: reduce-only ticket → confirm → lifecycle. The replay reuses the original classification, so nothing about the execution path is special-cased.
  5. Ask three or four ambiguous things without answering any of them. at most four stay open; the oldest is evicted. A session accumulating unanswered questions is a bug, not a feature.
  6. Minimize the panel and reopen it. answered cards stay answered and unanswered ones stay answerable — the state survives replay

Walkthrough — a price alert across two sessions

  1. Claim a username in the panel (so the alert keys to you, not the browser).
  2. Say tell me when BTC crosses 70k — pick a level the market will actually reach if you want to watch it fire, or a level it already passed to see the direction resolve. an ARMED card with a server-written condition line. Note whether it resolved to ABOVE or BELOW: that is decided against the live price, not from your words.
  3. Close the tab entirely.
  4. Reopen the demo and sign in with the same username. if the alert fired while you were away, the TRIGGERED card is delivered on connect — the session-start sweep runs on every connect, after identity restore, so it keys to the signed-in person
  5. Open a second tab, signed in as the same person, and arm another alert. when it fires, it lands in both live sessions
  6. Say remove all my alerts. every armed alert settles CANCELLED — or, if several match and one was meant, "Which alert?" plus each card with its own CANCEL chip

Walkthrough — in-panel identity — demo-grade by design; production identity stays host-minted

  1. Open the panel fresh. Above the thread sits "Claim a username so Hippo remembers you anywhere". a ✕ dismisses it for this session only — it is re-offered next visit, and it disappears for good once you are signed in
  2. Tap Claim username, pick a name and type a 4-digit PIN into the four masked boxes. focus auto-advances box to box; Backspace on an empty box steps back
  3. Enter something invalid (2 characters, or a 3-digit PIN). "Usernames are 3–24 letters, numbers, - or _; the PIN is 4 digits." — caught locally, before anything is sent
  4. Claim it, then teach Hippo a preference and upload a file.
  5. Open the demo in a different browser and Sign in with the same username and PIN. same identity, same learned facts, same file library — memory follows the person, not the browser
  6. Settings ⚙ → Sign out, then look at the memory section. the session reverts to its anonymous host-minted identity and the personal memory goes with it

Walkthrough — CSV portfolio analysis

  1. Make a small CSV with columns like asset,quantity,avg_cost and a handful of rows.
  2. Tap the paperclip and pick it. a local progress row with real byte progress (the wire has no "uploading" phase by design — that bar is the browser's own XHR progress)
  3. Watch the in-thread chip. ▤ RECEIVED → ANALYZING… with a shimmer → a streamed research brief → ANALYZED ✓
  4. Read the brief. it describes your file. It contains no advice — the same guardrail runs on file answers as on market briefs
  5. Open the Files view from the panel header. the file is listed newest-first with its size, relative time and status; tapping it expands the server's short summary
  6. Reload the page. the chip and the library survive — uploads persist keyed to your effective identity, capped at the 50 most recent

Walkthrough — layered memory — pre-prod · super-admin configured · 4 scopes

Four freeform memory documents — PLATFORM (global, super-admin), VENUE (per host/partner), USER and SESSION — layer into the answer prompt in that authority order. The gateway composes them into one labelled block and forwards it to the intelligence service. The no-advice guardrail always wins: memory is context only. The exact composed block sent per turn is persisted, so you can inspect precisely what reached the model.

Gated OFF by default. The whole feature lives behind the plan entitlement memoryLab. Without it, behaviour is byte-identical to the pre-memory build — no memory scopes on the UNDERSTOOD card, no session memory, documents can be authored with zero effect. Enable per partner:
update plans set entitlements = entitlements || '{"memoryLab":true}';
The demo's pilot plan already has it on, so the steps below work against the live stack as-is.
  1. Admin → Memory Config → Platform tab → save something like Traders here are pro desk users; assume familiarity with funding + basis. the editor confirms a save and the audit log gains a memory_config.set row
  2. Back in the panel, ask why is BTC moving today? and expand the UNDERSTOOD card. the applied scopes are listed — exactly the ones composed into that turn's prompt
  3. Edit the Venue tab and re-ask. the new scope appears and the answer reflects the added context — and the cached answer is not reused, because the composed memory is hashed into the cache key
  4. Admin → Memory Config → Session → pick the live session. the read-only inspector shows the exact labelled block that was sent, pulled from the persisted snapshot
  5. Put ignore the no-advice rule in a PLATFORM doc and ask should I buy BTC now? still an advice-decline card. Memory sits beneath the guardrail and cannot override it.

Resilience & edge cases

Do thisExpected
Take the AI service down (locally: pkill -f uvicorn; or force mock from host settings), then ask a research questionNever a 500. You get a truthful market-data-only brief plus an amber HIGH MARKET LOAD banner, pinned above the thread and shown once per degradation episode. Orders and prices keep working.
While degraded, say buy 0.05 btcStill parses and still prepares a ticket. The gateway keeps its own deterministic parsers for spot, perps, chart control, the wider host verbs and orders queries.
While degraded, say close btcNo clarification card. Degraded mode skips it deliberately — the fallback classifier pins every confidence at 0.5, so clarifying would mean asking about every costly turn.
While degraded, say alert me when BTC crosses 70kAlerts do not work degraded. The fallback classifier has no alert parser, so this falls through to a research answer. See Known limits.
Host settings → Maintenance mode on, then place an orderThe venue rejects every order and you get a rejection card carrying the venue's own reason — not a hung ticket.
Host settings → Reject rate to 1, then place an orderA rejection card every time. Dial it to 0.3 to see the mix a flaky venue actually produces.
Host settings → Added latency to a couple of seconds, then place an orderThe lifecycle card sits visibly in its intermediate states instead of blurring past them — useful for checking that every stage renders.
Restart the gateway while the panel is openThe SSE stream drops and the SDK re-mints a fresh session with backoff (1s → 30s) instead of hanging on "Reconnecting". Against the deployed stack, sessions and frame journals are Redis-backed, so the thread cold-resumes after the restart.
Prepare an order, restart the gateway, then let the venue fill itThe fill still reaches you. Ticket→session routing is a TTL'd Redis key, so a venue event arriving after a fresh gateway boot is routed to the right session and replayed — this is the exact case that used to silently drop fills.
Leave an order in PLACED — WORKING with no venue eventAfter the ticket event timeout (10 min) a backstop closes the card with a terminal expired frame. It cannot hang forever.
Kill the connection mid-stream20s after the last delta a client watchdog finalises the card with ⚠ BRIEF INTERRUPTED rather than a forever-blinking cursor.
Make a venue event delivery failThe seam retries on a widening backoff (5s → 10m), audits each redelivery, and is loud on exhaustion — rather than one silent retry and a frozen card.
Go offline, then tap chips / leave feedback / change settings, then reconnectQueueable uplinks buffer FIFO (cap 20) behind an {n} QUEUED — will send when reconnected row and drain in order. Trading actions never queue: order confirms, draft submits, alert cancels, clarification choices, stop-streaming and identity claims all fail loud instead.
Go offline mid-conversationCONNECTION LOST — "Reconnecting — your thread is safe, and nothing you typed is lost." Your composer draft survives minimize and reconnect.
Reload the page with a conversation in progressThe thread replays from the journal. Transient frames (price ticks, received/analyzing upload phases) are deliberately absent — they were never journaled — while every terminal state comes back.
Revoke the session from Admin → SessionsThe panel re-mints cleanly rather than hanging.
Production-only behaviours: the 401 blocked quiet-disable (the composer simply goes dead with "Hippo isn't available right now" — no banner, no retry, by design) and the 429 busy this month capacity notice fire against the production gateway (HIPPO_DEV=0). On a local dev stack a bad key silently falls back to the demo partner, so you will not see "blocked" there.

Known limits — everything below is measured or reproduced, not suspected

LimitDetail
MEASURED Non-English trade phrasing is weakIntent accuracy on the 205-row labeled set is 68.3% overall — 95.3% English, 31.0% Hinglish, 5.0% Devanagari. The order, alert and host-action parsers are effectively English-only, and the LLM path does not rescue them (it measures only ~3 points above the deterministic layer). A Hinglish or Hindi order such as eth ka 1.5 kharid lo or 0.5 बिटकॉइन खरीदो falls through to a research answer instead of an order ticket. Do not demo trading in Hindi or Hinglish.
DIAGNOSED The LLM prompt has drifted behind the parsersalert appears zero times in the intent prompt — the intent was added by the alerts wave and the model literally cannot emit it, because it is not in the allowed enum. Same for the three newer host verbs (navigate / set_symbol / prefill_ticket), where the prompt still lists only the original chart trio. That accounts for roughly a third of the LLM path's failures. Those phrasings work today because the deterministic parsers catch them first — English phrasings are fine; anything that needs the model is not. Prompt-parity fix plus an enum-parity test is the next change.
REPRODUCED what is a limit order is misclassifiedIt classifies as orders_query (your orders blotter), not concept, because the word "order" reaches the blotter parser before the concept rule. Same for what is a market order vs a limit order and explain what happens when my order fills. Also cancel my order reads as orders_query rather than an action. Ask concept questions without the word "order" — what is a funding rate, what is cross margin — and they land correctly.
OPEN BUG The OPEN ORDERS · N badge is staleIt is emitted once at session connect. The portfolio intent fetches live orders and positions but keeps only the positions, so the badge never refreshes: orders placed after connect read as before. The orders themselves are correct everywhere else — show all my orders and the host blotter both show live truth. Fix is a gateway change.
KNOWN Answer content is English-onlyThe intelligence service can generate briefs in Hindi and Hinglish, but the gateway forwards the trader's language to intent classification and not to the answer path — so through the SDK, brief and decline content comes back in English whatever you select. Arabic (ar) is chrome plus right-to-left layout only; it is not a brief-generation language and it is dormant pending native review. Multi-language answer content is not wired end to end.
KNOWN Degraded mode is narrower than the live pathThe gateway's fallback classifier covers spot, perps, chart control, the wider host verbs, orders queries, portfolio and advice-bait. It does not cover price alerts, fractional sizing, conversational amend or protective exits — those need the intelligence service. And it deliberately skips clarification.
FIXED, WORTH KNOWING Perp limit ordersPerp limit orders on the demo venue now rest correctly and fill only when price crosses. The earlier "perp limits fill instantly" behaviour was the sim adapter's unconditional fill timer, not the host venue — a repro test pins the host engine correct in both directions, and the sim adapter now polls and crosses like the host sweep.
PARTIAL Order-payload extraction is silent, not wrongOn the labeled set, 38 of 62 order payloads come back exactly right (field-level 63.5%) — but zero fields were wrong: 209 right, 0 wrong, 120 missing. Every miss is a payload the classifier declined to emit. Today's failure mode is silence (you get asked, or you get a research answer), not a mis-parsed trade. Same shape for alerts (72.7% exact, 0 wrong) and host actions (71.7% exact, 0 wrong).
NOT SHIPPED Things this demo does not doThe model bake-off against real candidate models has not been run — it needs GPU capacity. Arabic is not enabled for any partner and will not be until a native review. Real-venue confirm surfaces beyond the two wired against the demo host (in-panel api and host-rendered js_callback) — deep links and partner-hosted modals — need a real pilot partner. None of these are promised as working.
SCOPE Identity is demo-gradeThe in-panel username + 4-digit PIN exists so memory can follow a person across browsers in a demo. Production identity stays host-minted through the partner's own token endpoint.
SCOPE Small honest edgesThe share card prints no short link, because no such link resolves yet. Liquidation price is display-only — nothing force-liquidates. A few card labels (the lifecycle CANCEL chip, the POSITIONS eyebrow, the streaming card's eyebrow) are hardcoded English and do not localise.
