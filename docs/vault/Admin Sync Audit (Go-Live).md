**Verification:** Reproduced end-to-end: service.ts:559-565 swallows memory outages (and non-ok responses) into persona:null on the joined /v1/users route; users.tsx:279 returns early for registered users so the distinguishing /v1/memory route (502 vs 404) is never called; users.tsx:482 renders null as 'No memory held for this user.' with Clear/Purge hidden and no error banner. Aggravating fact the finding missed: memory service returns a default persona (200) for never-stored keys (memory/src/store.ts:137), so for registered users persona:null arises ONLY on outage/error — the 'No memory held' message on a registered user's page is essentially always an outage artifact stated as fact. Violates the service's own documented invariant (service.ts:604-608) that 'we hold nothing' must never be answered wrongly for deletion requests. An unset MEMORY_URL (same class as the known INTELLIGENCE_URL silent-null bug) makes it permanent and silent.

### Memory write/purge proxies skip URL-encoding that the read proxy performs
`services/admin/src/service.ts:640` · route-parity

**Claim:** GET /v1/memory/:partnerId/:userId re-encodes params when building the memory-service URL, but the sibling PUT (line 640), POST /clear (line 658), DELETE (line 674), the persona join in GET /v1/users/:partnerId/:userId (line 561), and the /v1/memory-config host/user scope proxies (lines 794-813) interpolate the decoded params raw, so the same user id resolves to different memory-service paths depending on verb.

**Scenario:** A user id containing a reserved character (e.g. stored as `u/1`, addressed by the SPA as `/v1/memory/p/u%2F1`): the admin GET re-encodes and the memory service returns the persona, but DELETE/PUT/POST-clear rebuild the URL as `/v1/persona/p/u/1` (three segments), which matches no memory-service route and 404s — the operator can see the persona but every purge/edit/clear against it fails, the exact 'deletion request must never get wrong' case the GET's own comment warns about. [unverified] whether production user ids currently contain such characters; the asymmetry itself is in the file.

**Verification:** Confirmed end-to-end, could not refute. (1) The asymmetry is exactly as cited: service.ts:614-615 encodes both params; the sibling PUT (line 640), POST /clear (line 658), DELETE (line 674), the persona join at line 561, and the memory-config host/user scope proxies (lines 794-813) interpolate decoded params raw. The learned-facts proxies (lines 713, 730, 750) and the bulk purge (line 689) encode, proving the intended pattern. (2) No rescue elsewhere: memoryFetch (service.ts:163-175) concatenates the path into fetch without encoding; the memory service routes are plain param routes (/v1/persona/:partnerId/:userId, /admin/personas/:partnerId/:userId per services/memory/src/service.ts:133-167), so a decoded `/` in userId adds a path segment and 404s, and a `?` or `#` truncates the path — a userId like `a?x` would make DELETE /admin/personas/p/a?x actually purge user `a`, a wrong-target deletion. (3) No charset constraint upstream: venueUserId is the partner JWT's `sub`, validated only as non-empty string (gateway plugins/auth.ts:596-600); panel identities (`id:<username>`) are safe, but host-minted subs are arbitrary partner input. (4) The SPA encodes params when building requests (apps/admin/src/pages/memory-config.tsx:52), and fastify/find-my-way decodes percent-escapes in params, so the encoded-in/raw-out round trip is reachable, not theoretical. Compounding wrinkle: the write proxies fire `record(op, 'memory.purge'|'memory.update'|'memory.clear', ...)` unconditionally before checking res.status, so the audit log records a purge/clear that actually 404ed — the operator's audit trail asserts a deletion that never happened. Severity: major, not blocker — the failure requires a partner-minted sub containing a reserved character (/ ? # %); typical subs (uuid, numeric, email — @ . + - _ are all path-legal) are unaffected, and [unverified] whether any pilot partner mints such ids. It is a broken operator workflow (GET shows the persona, every purge/edit/clear against it fails or, worse, hits the wrong key) on the exact GDPR-deletion surface, with a false audit record on failure — upgrade to blocker the moment any partner's subs contain reserved characters.
